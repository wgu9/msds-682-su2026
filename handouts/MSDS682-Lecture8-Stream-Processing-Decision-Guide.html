Choose the compute owner

A minimal stream-processing continuation: teach the decision that survives product changes—not a syntax tutorial.

The teaching decision

Syntax expires faster than architecture judgment

“Do not start with a product name. Start with the state, time, recovery, and ownership the system requires.”

Product direction, feature lifecycle, tenant availability, and pricing can change. The course should teach students how to re-evaluate tools from first principles.

Ask before naming a tool

Five stable questions

  1. State: must the system remember unmatched events or a current keyed answer?
  2. Time: do event time, windows, watermarks, or late records affect correctness?
  3. Scale: what throughput, state size, partitions, and operational load must be handled?
  4. Recovery: how will checkpoints, replay, dedupe, and failure recovery work?
  5. Ownership: does the team prefer SQL, application code, or a managed service boundary?

Minimal selection table

Choose the smallest owner that satisfies the contract

PathChoose it when…Do not choose it merely because…
Plain consumer One service validates, transforms, calls an API, or writes a store; state/time needs are small and explicit. “Every Kafka message needs a stream processor.”
Stateful SQL engine The hard part is a maintained table, join, aggregate, window, event time, or late-data policy and the team owns SQL operations. “SQL removes the need to define state, recovery, and deployment.”
Embedded processing library The team needs application-code control, typed logic, explicit tests, and one release owner for stateful processing. “Code is always more powerful than SQL.”

Three quick decisions

Match the tool to the hard part

Simple effect

Validate → call API → write result

One owner, bounded state, ordinary retry.

Likely choice: plain consumer.

Maintained table

Filter → group → current table

The current keyed result is the product; the team owns SQL operations.

Possible choice: stateful SQL engine.

Time + state

Quote → delayed outcome → windowed evaluation

Wait, join, late policy, recovery, and metrics are the core problem.

Possible choice: stateful engine or embedded library, depending on ownership.

There is no universal winner. The correct answer includes the requirement, the trade-off, and why the rejected alternatives are unnecessary or risky.

The durable mental model

Students need seven concepts—not a product tour

Operation

Filter / map

Keep or transform each event.

State

Aggregate

Maintain a running answer.

Relationship

Join

Match events across streams or tables.

Time

Window

Bound which events belong together.

Correctness

Watermark / late policy

Decide how long to wait.

Durability

Checkpoint / replay

Recover the same state after failure.

Contract

Key / schema

Define identity and compatible data.

Evidence

Output / metric

Show the maintained answer is correct.

Lecture 8 exit ticket

One sentence, three clauses

“My project needs this state/time behavior, so I choose this compute owner, and I will prove it with this failure or replay test.”

Final message: the tool name is not the answer. The requirement-to-tool reasoning is the answer.
