The mental model

Begin with two questions, not a framework

Question 1 · Memory

Is one record enough?

Yes: usually stateless. No: stateful because an earlier record must be remembered.

Question 2 · Meaning

History or current value?

Stream: every change. Table: the latest value by key.

State begins when one record is not enough. Stream versus table tells us how to interpret the history we retain.

The correctness map

Stateful work needs an explicit policy

QuestionWhat must be declared?
Which records belong together?Contract, key, and partition alignment

01
Operations

Choose the operation before adding state policy

  • Boundary: Kafka retains events; the processor computes.
  • Stateless: filter and map usually handle one record at a time.
  • Stateful: aggregate and join remember earlier records.

Responsibility boundary

Kafka stores the history; a processor interprets it

Kafka broker

Retain and deliver

Topics, partitions, offsets, replication, replay.

Processor

Compute and remember

Filter, transform, aggregate, join, classify, and emit.

Classroom scripts stay bounded for evidence; the production processor keeps polling as new records arrive.

Kafka is not the business computation. Client code or a processing framework performs that work.

Stateless operations

Filter decides; map transforms

Filter · one in → zero or one out

Keep valid trip requests

Evaluate a predicate against one record: required fields, valid coordinates, or a business threshold.

Map · one in → one out

Reshape one contract

Extract fields, convert units, or enrich from a fixed lookup before emitting a new record.

“Usually stateless” is deliberate. A changing lookup table or external history introduces state and failure policy.

Stateful operations

Aggregate updates a result; join completes a relationship

Aggregate · many → running result

Remember an accumulator

Group by key, update count or average, optionally bound by a window, then emit on update or close.

Join · two histories → one fact

Remember unmatched records

Correlate by key, apply a time or completion policy, emit a joined fact, then clean up state.

Demo 07 follows the Join column. Its state is visible in Python so matching, failure, and commit boundaries remain inspectable.

Two views of changing data

A stream records changes; a table represents current state

Stream

Every event matters

trip-requested, fare-quoted, trip-completed. History is append-oriented.

Table

Latest value by key

trip_id → latest trip status. Later updates replace the current view.

Stream and table are interpretations. Kafka topics remain ordered event logs.

A shared key is necessary for a keyed join, but not sufficient. Contracts, time bounds, state, and recovery policy still matter.

Two clocks

When did the event happen, and when did we process it?

ClockMeaningWhy it matters
Event timeTime recorded by the business eventWindows should reflect when the activity occurred

Demo 07 uses a finite classroom join. Production systems must state which clock governs expiry.

02
Stateful joins

Subscribing receives records; joining creates a relationship

  • Store the unmatched side by key.
  • Match when the other side arrives.
  • Expire or recover state under an explicit policy.

Common misconception

Two subscriptions do not automatically produce one joined fact

Subscribe

Receive both histories

The consumer sees quote records and outcome records.

Join

Implement correlation

Extract key, store unmatched input, match, compute, emit, and clean up.

The application owns the join semantics.

Lecture 7B synthesis

Return to the same map

  1. Ask whether one record is enough and whether you need history or current state.
  2. Choose the operation: filter, map, aggregate, or join.
  3. For stateful work, declare key, time, bounds, state, late-data, and delivery policy.
  4. Demo 07 applies Join: quote plus delayed outcome becomes an evaluation.
The operation says what to compute; the policy makes the result trustworthy.
